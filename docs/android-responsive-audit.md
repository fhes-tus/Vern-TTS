- **Reviewed** means the cited source and its layout behavior were checked. Runtime behavior is pending.
- **Finding** means the cited source contains a concrete sizing or placement assumption worth checking. A source finding is not a reproduced device defect.
- Promote a finding to **Reproduced** with a build, profile, steps and evidence. Use **Changed** after implementation and **Verified** only when the required configurations pass. Preserve any failed or unavailable configuration in the evidence table.
- Record OS/API, device or emulator profile, actual app window width and height in dp, density or display scale, font scale, locale, navigation mode, posture, input state and commit/build for each run. Record the test or screenshot path and observed result. A forced Compose size is component coverage. A real resize, fold, keyboard or launcher run is a separate result.
- Keep existing typography, themes, icons, glass styling, motion, cover proportions and navigation behavior as the baseline. Use measured parent constraints for component size and actual window dimensions for larger layout decisions. Keep intentional dimensions such as touch-target minima. Let text-heavy cards and controls grow or wrap, and give short windows a path to every primary action.

The official Android [edge-to-edge skill](https://github.com/android/skills/blob/main/skills/system/edge-to-edge/SKILL.md) informs the keyboard and inset checks. The [adaptive skill](https://github.com/android/skills/blob/main/jetpack-compose/adaptive/SKILL.md) informs window, state and posture coverage. Its full workflow assumes Compose for all screens and Navigation 3. This audit uses applicable guidance within Vern's existing Compose, Views and Glance architecture.
