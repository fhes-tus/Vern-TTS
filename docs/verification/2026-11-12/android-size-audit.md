# Android base-size and performance opportunities

12 November 2026, Reykjavík. Branch: `test/reader-ui-update`, HEAD `8f42a8e`, with the user's existing uncommitted Android changes retained. This is an audit of existing source and local build artifacts. This audit changed no application code, build configuration, resources, installed packages or device data, and rebuilt or published no release. The workspace remained active: the final status additionally showed changes to `ActualDocumentView.kt` and `VeritasPdfViewerActivity.kt` that this audit did not make or modify.

## Findings and priorities

The most promising incremental base-size work is to narrow the package-wide R8 keep rules, starting with Bouncy Castle. The largest remaining base payload is the native speech runtime; reducing it requires a custom, model-compatible native build or an explicitly optional runtime component. Smaller image optimizations can follow. Separately, eager full-book annotation loading and repeated whole-history/notes processing merit a performance investigation.

There is no measured before/after improvement from this audit. Figures below describe packaged contents, not guaranteed removable bytes or a diagnosis of the user's phone slowdown.

- `app/build.gradle.kts:84` already excludes the unused Sherpa C and C++ API libraries. Neither occurs in the inspected base payload. Deleting their source copies would save repository space, not app size.

- No `.onnx`, `.ort`, `.tflite` model or translation JNI entry was found in the inspected release base. Voice models are downloaded separately; shrinking those downloads would address user data/model storage rather than base packaging.

## 1. Narrow R8 rules, starting with crypto

**First incremental size experiment.** `app/proguard-rules.pro:17` preserves every Bouncy Castle class and member, preventing ordinary shrinking and optimization across the package. Similar broad rules cover PDFBox/Harmony (lines 22–23), AndroidX PDF (line 28), and ML Kit (lines 32–33).

The final release DEX actually contains:

| Recognizable package family | Defined classes | Defined methods | Instruction bytes |
| --- | ---: | ---: | ---: |
| Bouncy Castle | 6,289 | 35,030 | 2,433,710 |
| Of which `org.bouncycastle.pqc` (overlaps previous row) | 1,011 | 5,207 | 487,422 |
| PDFBox / FontBox / Harmony | 745 | 7,573 | 456,406 |
| AndroidX PDF | 595 | 3,671 | 154,944 |
| ML Kit and recognizable internal ML Kit packages | 2,259 | 6,011 | 376,904 |
| Sherpa Kotlin bindings | 13 | 333 | 10,460 |

Instruction bytes count DEX `code_item.insns_size * 2`; they exclude strings, metadata, tables, padding and debug information. They are **not** an estimate of removable code. Other DEX classes are obfuscated and cannot be assigned to dependencies from their descriptors alone. The current Bouncy Castle footprint contains code that deserves a reachability/algorithm audit, including post-quantum classes even though the Gradle exclusion already removes their jar resources.

Proposed experiment: preserve PDFBox's actual encryption/security-handler reflection needs, then progressively allow optimization/shrinking of unrelated crypto classes. Inspect R8's retained roots for representative PQC/provider classes and compare the resulting release DEX and device-specific APK. Keep the existing JNI, WorkManager/Room, widget and optional-feature reflection contracts intact. The merged release configuration already includes PDFBox's own narrower consumer rules for security handlers and document interchange; it is not relying only on the app's blanket PDFBox rule.

Full provider registration is dynamic, so simply deleting the entire crypto keep rule might still retain algorithms or break PDF handling. Treat this as a controlled release-build experiment rather than a promised multi-megabyte saving. Validate ordinary/encrypted/password-protected PDFs, CJK and embedded fonts, outlines/links, OCR and worker imports on a minified build, then exercise widgets and the installed/absent translation split. The existing `tools/r8-smoke/README.md` describes isolated-package checks and records why reflective constructors matter.

Android's [keep-rule guidance](https://developer.android.com/topic/performance/app-optimization/keep-rules-best-practices) recommends specific reflection contracts rather than long-term package-wide rules. No rules were changed in this audit.

## 2. Reduce the native neural runtime

**Largest remaining base-size area, with greater implementation/validation cost.** The two speech libraries alone are:

| ABI | ONNX Runtime | Sherpa JNI | Total raw speech payload |
| --- | ---: | ---: | ---: |
| ARM64 | 22,249,552 | 4,771,760 | 27,021,312 bytes (25.77 MiB) |
| ARMv7 | 15,359,576 | 3,428,780 | 18,788,356 bytes (17.92 MiB) |

Two distinct options need evaluation:

1. Build a pinned reduced-operator ONNX Runtime compatible with the existing Sherpa JNI and every supported Piper, Kokoro and Kitten model. A smaller kernel set is a documented [ONNX Runtime build option](https://onnxruntime.ai/docs/build/custom.html). The current app loads ONNX files, so blindly selecting a basic ORT-only minimal build would break that contract. Operator reduction needs the union of all supported model graphs and future-catalogue controls. Actual reduction and inference performance are unknown until built and tested.
2. Make the neural runtime itself an optional feature installed when neural speech is explicitly requested. Models are already optional; the native runtime remains in base. Moving it could remove most of the measured speech payload from the initial base for users who never install neural speech. It would not save that runtime's eventual storage for users who install it. This requires split/JNI loading, first-use/offline/error/cancellation/upgrade behavior, and both Play and sideload distribution handling. Existing speech choices must stay explicit.

Preserve current voice families, model precision, speaker mapping and audible quality. JNI configuration fields are read by native code: deleting unused-looking Sherpa configuration fields or blanket-kept bindings is not a safe shortcut. The bindings' entire instruction footprint is only 10,460 bytes anyway. `tts/NativeModel.kt` already lazily creates models and retires them; lazy model allocation is not a new fix.

## 3. Keep each sideload APK to one ABI

The inspected debug APK and retained installed-production APK contain both ARM architectures. An ARM64-specific sideload APK could omit the measured **18,795,608 raw bytes** of base ARMv7 libraries. This would retain support through a separate ARMv7 download. It does not require removing 32-bit support from the project.

This is a sideload/distribution opportunity. Play already supports ABI-targeted APK delivery from an AAB, so do not count the same saving again for a normal device-targeted Play install. No new APKs were generated, no channel/signature policy was changed, and no APK was installed. Actual APK length, download compression and Android's compiled-code storage require measurement.

## 4. Optimize images without changing appearance

The release retains **29 manual screenshots: 1,896,570 raw / 1,754,037 ZIP-compressed bytes**. The **39 bundled covers total 793,964 raw / 773,791 compressed bytes**. These are suitable for a WebP/re-encoding/resolution experiment with visual review of small text, covers and zoom behavior. The measured image pool is not the expected saving: only part can be removed by better encoding.

Keep existing covers and the manual available as designed. Four retained font entries total only **549,124 raw / 265,934 compressed bytes**; the source JetBrains Mono font is already absent from this release. Font/glyph/language removal is lower value and risks multilingual readability. Language splitting is deliberately disabled in source to keep all built-in interface languages available without a download. No images, fonts or translations were removed or converted.

PDFBox contributes **4,634,456 raw asset bytes / 1,618,605 compressed bytes**, including font mappings and a fallback font. Those assets support real PDF extraction/rendering, including CJK; wholesale deletion is inappropriate. Likewise, PDFBox and AndroidX PDF both have active source usages and serve different parts of import/extraction and native viewing. Removing one requires replacing and validating those functions.

## Performance opportunities independent of base size

**These are source-supported workload concerns, not measured causes of the reported slowdown.** Reducing package bytes alone cannot establish that scrolling, book opening or speech has become faster.

1. **Avoid loading every annotated book's full text in the main Library composition.** At audit time, `ui/screens/LibraryScreen.kt:281` launched on annotation IDs/documents, read each annotated book, chunked its entire text, then retained those lists in `loadedDocSentences`. The effect was declared before the Home/Library/Study/Notes tab switch and was not gated on opening Notes. Work occurred on I/O threads, but full text and chunk lists consumed heap and competed with startup/reading. **Follow-up correction:** tracing all consumers found this cache was unused. On the user's follow-up, removed only this duplicate preload and its two now-unused imports. `NotesHighlightsUi.kt` already has a separate lazy loader inside its visible list items, retaining only annotated sentences. That working loader, all saved data, anchors and callbacks were left unchanged. No new cache, migration or data deletion was needed. Runtime savings remain unmeasured; source line numbers above describe the audit snapshot before removal.
2. **Reduce duplicate startup parsing.** `ui/ReaderViewModel.kt:124` loads general notes for pending vocabulary recovery; the WorkManager observer at line 133 reloads all notes; the main startup pipeline at line 173 loads notes again, plus trash, annotations, note text, AI history and other collections before publishing its populated state. `DocumentRepositoryNotesAndStudy.kt:268` and `:283` each parse the same stored general-notes JSON for active/trash views. Share a validated snapshot for a load, publish essential Home/library state earlier, and fetch heavier content on demand while preserving counts and recovery work.
3. **Avoid repeated full session-history aggregation.** `DocumentRepositoryReadingSessions.kt:7` reparses, deduplicates and sorts the complete saved session array. `DocumentRepositoryReadingTracker.kt:51` reads it for daily/week totals; `DocumentRepository.kt:185` reads it again through `measuredReadingTimes`. The session-change observer at `ui/ReaderViewModel.kt:116` refreshes both results. Cache a consistent snapshot/aggregate with invalidation for live updates, corrections, restore, exclusions and deletion. Do not discard history or invent totals.
4. **Gate widget data work by actual installed instances.** `MainActivity.kt:220` requests a widget update at launch, and `VeritasWidgets.kt:203` dispatches six widget updates. Requests are already conflated and run off the UI thread. Check actual Glance instance behavior and trace repository work before adding an optimization; there is no evidence here that all six views actually render without installed widgets.

For before/after timing, use a release-equivalent isolated package and the same device/library, comparing cold/warm startup, Home/Library readiness, scroll frame timing, annotated-book opening and speech first-audio latency. Record installed APK/split bytes separately from user documents/models/cache and compiled code. Android recommends a non-debuggable, preferably minified [Macrobenchmark target](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview). No benchmark, phone run, network-off acceptance or inference test was performed here.

## Follow-up: translations, assets and code cleanup

Additional read-only checks on 12 November 2026 changed the priority of easy asset work. No further application or Gradle changes were made during these checks.

- **Built-in translated text is small.** Source XML inspection found 2,235 string entries per translated language. The nine non-English packs contain 817,731 UTF-8 text bytes total (798.57 KiB), excluding XML markup/plurals. Only 265 translated entries exactly match their English XML values, representing 2,408 text bytes. Source text totals are not APK savings. Removing languages or replacing them with machine translation would change offline availability and wording. The translation engine is already outside base.
- **Dependencies bring additional locale variants.** Parsing the retained release's `base/resources.pb` found 88 locale/default buckets across strings and plurals. Of these, 78 differ from the exact built-in/default tags, including regional variants of supported languages. They contribute 369,060 simple-string UTF-8 bytes and 632,734 serialized configuration/value bytes. Neither is a removable-byte estimate. Filtering these resources could change PDF, widget or component language fallback. This deserves a scoped language-matching audit, not a blanket deletion. The decoder follows AOSP's [Resources.proto](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/tools/aapt2/Resources.proto) and [Configuration.proto](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/tools/aapt2/Configuration.proto).
- **Measured PNG lossless gains are tiny in the existing release.** Recompressing only PNG IDAT streams while preserving every non-IDAT chunk and identical inflated scanline bytes reduced nine source PNGs by 23,179 bytes total. For the eight corresponding PNGs actually packaged in the retained release, the additional raw-file saving was only **2,192 bytes**. This is not a rebuilt APK or Play-download delta. R8's `resources.txt` explicitly marks the large `vern_book_earbuds_mark` and unused JetBrains Mono resource unreachable in this release; optimizing or deleting those source files would not reduce this artifact. The build already optimizes some source PNGs. Only candidate copies were written under `.artifacts`.
- **No identical-file deletion opportunity was found** by SHA-256 grouping all current app assets and `drawable-nodpi` files. JPEG/manual/cover re-encoding remains a format/quality experiment; no verified WebP saving is claimed. A bundled Android Studio libwebp JNI probe failed to resolve `wrap_WebPEncodeLosslessRGBA`, even with explicit DLL loading, so its attempted output is not evidence of a successful encoding.
- **General code cleanup is not a size measurement.** Unused code/resources may already be excluded from a release; deleting source files then helps maintainability/debug builds rather than installed size. Continue to inspect release reachability instead of removing core PDF, font or speech support from source appearance alone.
- **Further performance work has clearer targets.** `loadGeneralNotes` and `loadTrashedGeneralNotes` each parse the same complete JSON array, and startup calls both. A shared validated per-load snapshot could avoid that duplicate work without discarding history or notes. `LibraryNotesTab.kt:569` calls `formatMediaDuration` within a Compose `remember` calculation, and `LibraryNoteCardsUi.kt:157` has a similar fallback. These perform local file/media-metadata work on the composition path. Fetching/caching durations off the UI thread could preserve playback and visible duration values while reducing UI stalls. Neither change was implemented or benchmarked in this follow-up.

The Java probe failed as noted; `node .artifacts/size-audit-20261112/resource-details.cjs` completed the resource/PNG inventory.
